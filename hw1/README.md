# ДЗ №1 — аналитическая модель производительности CNN

Аналитическая оценка FLOPs, памяти, времени и энергии небольшой CNN.
Память, время и энергия сопоставлены с измерениями на Tesla T4.
Измерены все **132 конфигурации** из задания; нехватки памяти (OOM) не было.

## Модель и формулы

Сеть из [models.py](models.py) повторяет таблицу задания: шесть свёрток с ReLU,
MaxPool, GlobalAvgPool и два Linear. Всего **1 040 324 параметра**.
Свёртки без bias, Linear с bias, ReLU — inplace. BatchNorm не добавлен:
его позиции в таблице задания не указаны.

`S` — сторона изображения в пикселях, кратная 16; `B` — число изображений
в одном запуске. Приняты 1 MAC = 2 FLOPs и одна операция на сравнение.

| Величина | Формула | Единица |
|---|---|---|
| FLOPs | `F = B·(17751·S² + 313956)` | операций |
| Пиковая память | `M = 4161296 + 52·B·S²` | байт |
| Чтение и запись данных | `Q = 364·B·S² + 8592·B + 4161296` | байт |
| Время | `T = t0 + Σᵢ max(Fᵢ/C, Qᵢ/β)` | секунд |
| Энергия | `E = P0·T + εF·F + εQ·Q` | джоулей |

Память включает веса, сохранённый исходный вход и одновременно живые активации.
Временные буферы свёрток, индексы MaxPool и округления выделений исключены.
Для Q вход и веса каждого слоя читаются один раз, выход записывается один раз.
`Fᵢ` и `Qᵢ` — операции и байты отдельного слоя. В формуле T слои выполняются
последовательно, а вычисления и передачи данных
внутри слоя перекрываются. `C` и `β` — общие для всех слоёв постоянные скорости;
`t0` учитывает накладные расходы. Для энергии коэффициенты также постоянны.

## Условия эксперимента

Замеры выполнены **25.09.2026**, на одной Tesla T4 с доступными **14.56 GiB**.
Python 3.13.15, PyTorch 2.11.0+cu128, CUDA 12.8, cuDNN 9.19.0,
драйвер 580.82.07. Полное окружение — в [environment.json](results/environment.json).

- Случайные входы, seed 42; FP32, `eval()` и `inference_mode()`.
  `cudnn.benchmark`, `cudnn.allow_tf32` и `cuda.matmul.allow_tf32` выключены.
- Время — медиана 30 запусков после 10 прогревочных, с синхронизацией CUDA.
- Память — `torch.cuda.max_memory_allocated()` за отдельный прогретый forward,
  включая веса и вход.
- Энергия — расход всей GPU за серию запусков не короче двух секунд,
  делённый на их число; потребление простоя не вычитается.

На **63 базовых точках** подобраны параметры времени, затем энергии.
Остальные **69 точек** использованы для проверки (validation).
Минимизировался средний квадрат относительной ошибки. Параметры сохранены
в [theta.json](results/theta.json); формулы FLOPs и памяти не подгонялись.

## Выводы

**На малых входах существенны накладные расходы (launch-bound).** При S=32
увеличение B с 1 до 16 меняет время с 0.607 до 0.577 мс, хотя операций становится
в 16 раз больше. Это согласуется со слабой загрузкой GPU и заметными расходами
на запуск. В модели `t0 = 0.4315 мс` составляет 89% и 78% предсказанного времени
этих точек. Отдельное время запуска CUDA-ядра не измерялось.

**Ограничения по памяти и вычислениям зависят от слоя.** У ReLU мало операций
на каждый прочитанный и записанный байт; в нашей модели его время определяется
обменом с памятью (memory-bound). У Conv5×5 на больших входах преобладает
вычислительная часть (compute-bound). В одной сети оба ограничения могут
действовать одновременно. Три последовательных режима для всей сети
экспериментом не установлены; для этого нужны времена отдельных слоёв
и показатели загрузки GPU.

**Постоянные скорости не описывают смену алгоритмов.** При S=512 переход
B=65→70 увеличивает batch на 7.69%, время — на 70.66% (83.40→142.34 мс),
энергию — на 71.00%. Формулы предсказывают рост примерно на 7.65%.
В [профиле ядер](results/kernels.csv) одновременно меняется реализация первой
свёртки: появляются FFT-ядра. Это объяснение согласуется с наблюдениями,
но отдельный вклад смены алгоритма в задержку не измерен.

**Базовая формула памяти занижает все 132 измерения.** Для S=512, B=256
она даёт 3.25 GiB, измерено 5.75 GiB. Формула исключает индексы MaxPool
и рабочие буферы свёрток, которые выделяет PyTorch. Вклад каждого буфера
отдельно не записан, поэтому весь разрыв нельзя приписать одному из них.
Максимум по формуле — 3.25 GiB при доступных 14.56 GiB, поэтому модель также
предсказывает отсутствие OOM во всей сетке. Это совпало с результатом прогона,
хотя сам расход памяти занижен. Граница OOM экспериментально не достигнута.

**Энергетические коэффициенты описывают этот эксперимент.** Ошибка времени
может переноситься в член `P0·T`. Полученное `εQ = 0` не означает, что память
не потребляет энергию: время, FLOPs и Q сильно связаны, поэтому их вклады
трудно разделить. Модель отражает общий рост затрат, но заметно ошибается
в отдельных точках. Проверка относится к одной T4 и измеренному диапазону S, B.
