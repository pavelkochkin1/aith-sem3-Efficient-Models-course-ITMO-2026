# Подробности эксперимента и воспроизведение

Основные формулы, результаты и выводы — в [README.md](README.md).
Здесь приведены настройки и команды, необходимые для повторения работы.

## Сетка и порядок измерений

| Величина | Базовые значения | Дополнительные значения, seed 42 |
|---|---|---|
| S, пиксели | 32, 64, 128, 224, 256, 384, 512 | 48, 112, 448, 496 |
| B, изображений | 1, 2, 4, 8, 16, 32, 64, 128, 256 | 65, 70, 78 |

Измерены все 11 × 12 = 132 сочетания. Для подбора параметров использованы
7 × 9 = 63 базовые точки. Остальные 69 содержат дополнительный S или B
и служат для проверки. Разделение задано до измерений.

Сеть и сетка используют seed 42; случайный вход каждой точки — seed
`42 + S*257 + B`. Данные имеют формат NCHW и тип FP32.
Сеть работает в `eval()` и `inference_mode()`. Настройки PyTorch:

```python
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.allow_tf32 = False
torch.backends.cuda.matmul.allow_tf32 = False
torch.backends.cudnn.deterministic = False
torch.use_deterministic_algorithms(False)
```

Для каждой точки [measure.py](measure.py) выполняет следующие шаги:

1. Создаёт вход и делает 10 прогревочных запусков.
2. Сбрасывает счётчик пика памяти и выполняет один forward. Пик включает
   веса и исходный вход; начальная занятость памяти не вычитается.
3. Измеряет 30 forward через `perf_counter`, синхронизируя CUDA до и после
   каждого запуска. В CSV записывает медиану. Генерация входа в замер не входит.
4. Измеряет энергию отдельной серией длительностью не менее двух секунд.
   Разность счётчика NVML в миллиджоулях делится на 1000 и число forward.
   Это средняя энергия одного запуска всей GPU, включая потребление простоя.
5. Отдельно записывает имена GPU-ядер через PyTorch profiler. Внутри профайлера
   есть ещё 10 прогревочных forward: это обход
   [потери первых CUDA-событий после простоя](https://github.com/pytorch/pytorch/issues/192021).
   Имена получены для всех 17 вычислительных слоёв; Flatten отдельного ядра не создаёт.

Результат предыдущего forward освобождается перед следующим. Профайлер не входит
в замеры времени, памяти и энергии. При OOM сохраняется статус без числовых
результатов; при сбое счётчика энергии или профайлера сохраняется текст ошибки.
Каждая завершённая точка сразу записывается в CSV.
Описание счётчика энергии: [NVML API](https://docs.nvidia.com/deploy/nvml-api/api/group__nvmlDeviceQueries.html).

Прогон 25.09.2026 занял около 28 минут. Получены 132 успешные точки и 3960
отдельных замеров времени. Полные версии ПО, включая NumPy 2.1.3, объём памяти
и UUID GPU записаны в [environment.json](results/environment.json).
Повторение тех же настроек не гарантирует одинакового времени: частоты GPU
и условия виртуальной машины могут меняться.

## Подбор параметров

[calibrate.py](calibrate.py) использует только 63 базовые точки и минимизирует:

```text
mean(((prediction - measurement) / measurement)**2)
```

У всех точек одинаковый вес в относительной метрике. Сначала подбирается время:
`scipy.optimize.least_squares` запускается из девяти фиксированных начальных
приближений. Из сошедшихся решений выбирается наименьшая ошибка на базовых точках.
Параметры ограничены: `t0 >= 0`, `C > 0`, `beta > 0`.
Для устойчивости расчёта используются переменные `t0/1e-3`, `1e12/C`, `1e11/beta`;
численные границы записаны в [theta.json](results/theta.json).

Затем параметры времени фиксируются. Для энергии `scipy.optimize.nnls`
подбирает неотрицательные коэффициенты при предсказанном времени, FLOPs и Q.
Столбцы сначала приводятся к сопоставимому масштабу, а после подбора коэффициенты
возвращаются в исходные единицы. Измеренное время в энергетическую формулу
не подставляется. OOM и отсутствующие значения пропускаются, а не заменяются нулями.
Документация методов: [least_squares](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.least_squares.html),
[nnls](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.nnls.html).

| Параметр | Значение | Смысл в модели |
|---|---:|---|
| t0 | 0.4315 мс | Постоянные накладные расходы |
| C | 7.170 × 10¹² FLOP/с | Скорость вычислений |
| beta | 8.870 × 10¹⁰ байт/с | Скорость обмена с памятью |
| P0 | 65.422 Вт | Коэффициент при времени в формуле энергии |
| eps_F | 1.161 × 10⁻¹² Дж/FLOP | Коэффициент при числе операций |
| eps_Q | 0 Дж/байт | Коэффициент при объёме чтения и записи |

Эти числа описывают совместную подгонку модели. C и beta не измерялись отдельно
как характеристики оборудования; P0 не является измеренной мощностью простоя.
У энергетической задачи число обусловленности после нормировки столбцов — около
1103: время, FLOPs и Q сильно связаны, поэтому небольшие изменения данных могут
заметно менять отдельные коэффициенты. Значение eps_Q=0 получено на границе
допустимых неотрицательных значений.

В код нужно передавать `parameters["latency"]` в `latency()` и
`parameters["energy"]` в `energy()`, где `parameters` — содержимое `theta.json`.
Формулы принимают числа и NumPy-массивы с broadcasting.

## Пояснения к графикам и выводам

На графиках времени, энергии и памяти все панели одной величины используют
общие логарифмические оси. Чёрная линия вычислена по формуле. Измерения между
точками не интерполируются. Для времени показан межквартильный интервал
30 повторов; это наблюдаемый разброс, не доверительный интервал.
Для энергии и памяти интервалы неопределённости не оценивались.

На [карте ошибок](results/figures/validation_errors.png) слева показаны измерения
против предсказаний и линия идеального совпадения. Справа ошибка равна
`100*(prediction-measurement)/measurement`: отрицательные значения означают
занижение. Серые клетки — базовые точки, исключённые из этой карты.
Группы проверки имеют разный состав: при B=65,70,78 представлены все 11 S,
при остальных B — только четыре дополнительных S. Это нужно учитывать
при сравнении средних ошибок между группами.

Худшие проверочные точки по абсолютной относительной ошибке:

| Величина | S, B | Измерение | Предсказание | Ошибка |
|---|---|---|---|---|
| Время | 48, 256 | 6.200 мс | 3.534 мс | −42.99% |
| Энергия | 32, 78 | 0.10483 Дж | 0.05850 Дж | −44.20% |
| Память | 32, 78 | 40.45 MiB | 7.93 MiB | −80.39% |

Для [примера смены ядер](results/figures/kernel_transition.png) выбраны S=512
и B от 64 до 78; оси здесь линейные. При B=65→70 имена `scudnn` первой свёртки
сменяются на `fft2d_*` и `volta_gcgemm_*`. Такое различие между B=65 и B=70
наблюдается у всех 11 S. Точный порог переключения не измерен.
Для S=512 межквартильные интервалы времени равны 82.93–83.66 и 141.86–142.70 мс.
Скачок больше наблюдаемого разброса внутри этих серий, однако единственная
причина изменения времени не установлена. MAPE времени при B=65,70,78
составляет 8.78%, 35.50%, 33.70% соответственно, по одинаковым 11 размерам S.

В послойной модели граница между ограничением памятью и вычислениями проходит
при `F_i/Q_i = C/beta ≈ 80.84 FLOP/байт`. У ReLU это отношение равно 1/8,
а у Conv5×5 при больших BS² стремится к `6400/24 ≈ 266.7`.
Такой расчёт предполагает достаточную загрузку GPU. Его ограничения описаны
в [руководстве NVIDIA](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html#understanding-performance).

Пропущенные в базовой оценке памяти буферы видны в исходниках PyTorch 2.11:
MaxPool вызывает [вариант с индексами](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/native/Pooling.cpp#L128-L152),
а cuDNN выделяет [рабочую память выбранного плана](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/native/cudnn/Conv_v8.cpp#L354-L365).
Их отдельные пики в эксперименте не записывались. Формула памяти оставлена
базовой, с коэффициентом 52; он не подбирался по измерениям.

## Полный запуск через Colab CLI

Все команды выполняются из корня репозитория. Используется официальный
[google-colab-cli](https://github.com/googlecolab/google-colab-cli) версии 0.7.2.
Для этой версии установлен форк `jupyter-kernel-client` от Google: с обычной
версией из PyPI возникала ошибка `AttributeError: JupyterSubprotocol`.

```bash
uv tool install google-colab-cli==0.7.2 --with 'jupyter-kernel-client @ git+https://github.com/googlecolab/jupyter-kernel-client.git@f18e982c3265df5e923aa9def101ab3fd737e139'
colab version
colab --auth oauth2 new -s hw1 --gpu T4
```

При первом входе нужно открыть ссылку Google и вставить выданный код в тот же
терминал. Если возникла ошибка `Warning: Scope has changed`, а выданные разрешения
содержат `colaboratory`, повторить вход с новой ссылкой и новым кодом:

```bash
OAUTHLIB_RELAX_TOKEN_SCOPE=1 colab --auth oauth2 new -s hw1 --gpu T4
```

Флаг разрешает OAuthlib принять изменившийся набор разрешений только для этой
команды; дополнительных прав Google он не выдаёт.

Установить зависимости, загрузить модули и выполнить сетку:

```bash
colab install -s hw1 -r hw1/requirements.txt
for file in models.py equations.py measure.py check_environment.py requirements.txt; do
  colab upload -s hw1 "hw1/$file" "/content/$file" || break
done
colab restart-kernel -s hw1
colab exec -s hw1 --timeout 3600 <<'PY'
import measure
measure.main('grid')
PY
```

Colab CLI использует `uv` на удалённой машине. Установленный CUDA PyTorch
обновлять не нужно. Скрипт [check_environment.py](check_environment.py)
проверяет GPU и сохраняет её фактическую модель, UUID, версии ПО и настройки.
Каждый `colab exec` начинает работу в `/content`; файл `measure.py` нужно
импортировать как модуль, поскольку для записи контрольных сумм используется
`__file__`. После изменения загруженных модулей нужно перезапустить ядро.

Скачать результаты:

```bash
for file in environment.json protocol.json measurements.csv kernels.csv latency_samples.csv; do
  colab download -s hw1 "/content/results/$file" "hw1/results/$file" || break
done
```

Перед остановкой проверить, что файлы скачаны целиком и в `protocol.json` есть
`completed_at_utc`. После этого освободить GPU:

```bash
colab stop -s hw1
```

Перед повторным экспериментом нужно сохранить прежние результаты отдельно.
Скрипт измерений отказывается перезаписывать существующий `measurements.csv`.
Файлы на временной машине Colab исчезают вместе с сессией.

## Калибровка, графики и файлы результатов

Обработка сохранённых измерений выполняется локально, без GPU:

```bash
uv run --with-requirements hw1/requirements-calibration.txt python hw1/calibrate.py
uv run --with-requirements hw1/requirements-plots.txt python hw1/plot_results.py
```

Калибровка создаёт `theta.json`, `calibration_metrics.json` и `predictions.csv`.
Для графиков достаточно второй команды, если эти файлы уже есть.
[plot_results.py](plot_results.py) сверяет 132 предсказания с CSV, медианы времени
с повторами и контрольные суммы данных и исходников с записью калибровки.
Если входы изменились, сначала требуется повторить калибровку.

| Файл в results/ | Содержимое |
|---|---|
| [measurements.csv](results/measurements.csv) | S, B, время, память, энергия, статус и признак проверочной точки |
| [latency_samples.csv](results/latency_samples.csv) | Все 3960 отдельных замеров времени |
| [kernels.csv](results/kernels.csv) | Имена GPU-ядер по слоям и конфигурациям |
| [environment.json](results/environment.json) | GPU, версии ПО и настройки PyTorch |
| [protocol.json](results/protocol.json) | Сетка, seed, повторы, время начала и окончания, контрольные суммы исходников |
| [theta.json](results/theta.json) | Параметры, метод подбора, версии библиотек и контрольные суммы |
| [predictions.csv](results/predictions.csv) | Измерения, предсказания и ошибки каждой точки |
| [calibration_metrics.json](results/calibration_metrics.json) | MAPE, медиана и 95-й процентиль ошибки, относительный RMSE и RMSE |
| [analysis.json](results/analysis.json) | Ошибки по S и B, худшие точки и различия имён ядер |

Контрольные суммы SHA-256 позволяют проверить, что файлы соответствуют версии,
использованной при расчёте. Локальная калибровка выполнена на Python 3.12.11,
NumPy 2.5.3 и SciPy 1.18.1; для графиков использован Matplotlib 3.11.2.
Это отдельное окружение от GPU-сессии Colab, где собирались измерения.
